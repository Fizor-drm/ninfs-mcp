# ninfs-mcp Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ninfs CLIをsubprocessラッパーで叩くstdio MCPサーバー (5ツール) のMVPを実装する。

**Architecture:** `policy.py` (workspace containment + sanitizer + read-only強制) を土台に、`runner.py` (MountSession所有・stdout隔離・逆順cleanup) が状態を持ち、`server.py` は薄い5ツールの公開層に徹する。実機mountは全てmockし、単体試験のみで検証する。

**Tech Stack:** Python (src layout), `mcp` (stdio server), `ninfs` (CLI subprocess経由のみ、importしない), `pytest` (mockはstdlib `unittest.mock`)

**Spec:** `docs/superpowers/specs/2026-10-07-ninfs-mcp-design.md` (rev2)

## Global Constraints

- Windows + WinFsp 特化。実機mountの結合試験は手動とし、CI/単体試験では回さない。
- 接続は stdio。子プロセスの stdout/stderr は必ずパイプ capture し、継承しない。
- mount は全て read-only 強制。SD への write API・削除 API は作らない。
- AI に任意コマンド実行は渡さない。公開ツールは5個 (`detect_sd/mount_sd/find_title/extract_code/unmount`) のみ。
- `boot9.bin` / `movable.sed` の中身・SD復号キーを返さない。`ID0:` / `Key:` 行はログにも残さない。
- 共通 sanitizer をログ・MCP応答・subprocess stderr 要約の全経路に通す。
- コピー先は専用 workspace 配下のみ。正規化後のパスが workspace 配下かで判定する (`Path.resolve()` + `is_relative_to`)。
- 依存バージョンは `pyproject.toml` に pin し、`--decompress-code` 等の CLI 引数と出力名を実装時に照合する。
- ファイル内容は MCP 応答に含めない。`extract_code` はメタデータ (パス・サイズ・SHA-256・選択エントリ名) のみ返す。

## File Structure

- Create: `pyproject.toml` — src layout、Python>=3.10、`mcp`/`ninfs` をpin、`pytest` をtest依存に。
- Create: `src/ninfs_mcp/policy.py` — `resolve_dest` / `sanitize` / `reject_write_args`。状態を持たない。
- Create: `src/ninfs_mcp/runner.py` — `MountSession`/`TitleHandle` と5操作の実体。唯一状態を持つ。
- Create: `src/ninfs_mcp/server.py` — stdio エントリ。5ツールのスキーマと runner への委譲のみ。
- Create: `tests/test_policy.py` — policy の5観点。
- Create: `tests/test_runner.py` — runner の正常系・異常系 (subprocess は mock)。
- Create: `tests/test_server.py` — 5ツール登録・引数検証・エラー写像 (runner は mock)。※specの2ファイル構成にserver試験を追加する計画判断。実装コードは増やさない。

固定シグネチャ (全タスク共通、変更禁止):

```python
# policy.py
def resolve_dest(workspace: Path, dest_rel: str) -> Path: ...
def sanitize(text: str, secrets: Iterable[str] = ()) -> str: ...
def reject_write_args(extra: Mapping[str, Any]) -> None: ...

# runner.py
@dataclass
class MountSession:
    mount_id: str
    mount_point: Path
    children: list[str]  # 確保順: ["sdtitle", "ncch", "exefs"]
    title_handles: dict[str, TitleHandle]

@dataclass
class TitleHandle:
    handle_id: str
    mount_id: str
    requested_title_id: str
    resolved_title_id: str
    kind: str  # "base" | "update"

def detect_sd(sd_root_override: str | None = None) -> dict: ...
def mount_sd() -> MountSession: ...
def find_title(session: MountSession, title_id: str) -> TitleHandle: ...
def extract_code(handle: TitleHandle, dest_rel: str) -> dict: ...
def unmount(mount_id: str) -> dict: ...
```

`extract_code` の戻り値は `{"dest_path": str, "size": int, "sha256": str, "code_entry": str}`。`unmount` の戻り値は `{"ok": bool, "incomplete": bool, "errors_sanitized": list[str]}`。

環境変数 (計画で確定。specは BOOT9/MOVABLE/SD_ROOT のみ定義のため workspace を追加する):
- `NINFS_BOOT9_PATH`, `NINFS_MOVABLE_PATH`, `NINFS_SD_ROOT` (任意), `NINFS_WORKSPACE` (必須。絶対パス。存在しなければ作成)。

## Review Focus

specが黙っているが利用者が当然期待する振る舞い。各行のテストは所有タスクに組み込み済み。

1. `dest_rel` に `\\server\share\x` や `C:foo` や `/` `\` 混在を渡しても workspace 外に書けない → 拒否される (Task 1)。
2. ninfs の stderr に秘密フルパスや `Key: <hex>` が含まれても MCP 応答に出ない → マスクされる (Task 2)。
3. 圧縮 `.code` の ExeFS では展開済みが選ばれる → `code-decompressed.bin` 優先、無ければ `.code` (Task 3)。
4. 子mountの解除に失敗しても公開IDは無効化され、残存は報告される → `incomplete: true` (Task 2)。
5. `NINFS_SD_ROOT` がSDでないパスでも mount しない → `detect_sd` で検証エラー (Task 2)。

- [ ] **Step 3: Implement runner基盤**

`_spawn_ninfs(argv, timeout)`: `subprocess.Popen(argv, stdout=PIPE, stderr=PIPE, stdin=DEVNULL)` で起動し `communicate(timeout=...)`。stdout は読み捨て (変数に残さない)。stderr は `sanitize(decoded, [boot9, movable, sd_root])` した要約 (末尾2000字) のみ例外に含める。`TimeoutExpired`時は `kill()` 後に `communicate()` し逆順cleanupしてから例外化。
`detect_sd`: `NINFS_SD_ROOT` 指定時はその配下の `Nintendo 3DS` 有無だけ検証する。未指定時はドライブ列挙 (Windows: `A:`〜`Z:` の存在するもの) で `Nintendo 3DS` ディレクトリを持つ候補を集め、0件→エラー、1件→採用、複数→`ambiguous`。
`mount_sd`: `uuid4().hex` を発行し、ninfs `mount_sd --movable ... --boot9 ... <sd> <mountpoint> -o ro` 相当を `_spawn_ninfs` 経由で起動 (正確な引数は Task 3 の照合と合わせて pin 版で確定し、ここでは `--help` 照合済みの値を定数 `SD_MOUNT_ARGS` に置く)。`reject_write_args({})` を通過させる。
`unmount`: 公開IDをレジストリから即削除し、children を逆順解除。1件でも失敗したら残りを継続し `incomplete: True` + sanitizer済み理由を返す。

- [ ] **Step 3: Implement `find_title` + `extract_code`**

`find_title`: ベースID末尾 `00040000...` に対応する更新ID (`0004000E...`) の存在確認を SD Title mount 上で行い、更新優先で解決。TMD複数時は更新 > バージョン最大 > 先頭。`sdtitle → ncch → exefs` の順で `_spawn_ninfs` し、exefs には `--decompress-code` を付ける。成功時のみ `TitleHandle` を発行・登録。
`extract_code`: ExeFS内エントリ列挙で `code-decompressed.bin` > `.code` > `code.bin` の順に選択。`resolve_dest(NINFS_WORKSPACE, dest_rel)` で送り先を確定し、`shutil.copyfile` + `hashlib.sha256` でコピーとハッシュ化。戻り値はメタデータのみ。
