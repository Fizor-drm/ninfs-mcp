# ninfs-mcp Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ninfs CLIをsubprocessで駆動するstdio MCPサーバー (5ツール) のMVPを実装する。

**Architecture:** `policy.py` (形式拒否+包含確認・sanitizer・read-only強制) を土台に、`runner.py` が常駐 mount プロセス (`spawn`→readiness→`terminate`) と `MountSession` 所有・逆順cleanup・残存管理を持ち、`server.py` は公開スキーマと委譲だけの薄層に徹する。実機mountは全てmockし、単体試験のみで検証する。

**Tech Stack:** Python (src layout), `mcp` (stdio server), `ninfs` (CLI subprocess経由のみ、importしない), `pytest` (mockはstdlib `unittest.mock`)

**Spec:** `docs/superpowers/specs/2026-10-07-ninfs-mcp-design.md` (rev2 + long-lived/形式拒否/`NINFS_WORKSPACE`必須の追補)

## Global Constraints

- Windows + WinFsp 特化。実機mountの結合試験は手動とし、CI/単体試験では回さない。
- 接続は stdio。ninfs mount CLI はブロックする常駐プロセスとして `Popen` 起動し、`communicate` 待ちはしない。stdout は DEVNULL へ捨て、継承しない。
- mount は全て read-only 強制。SD への write API・削除 API は作らない。
- AI に任意コマンド実行は渡さない。公開ツールは5個 (`detect_sd/mount_sd/find_title/extract_code/unmount`) のみ。
- `boot9.bin` / `movable.sed` の中身・SD復号キー (`ID0:` / `Key:` 行) を返さない。ログにも残さない。
- 共通 sanitizer をログ・MCP応答・subprocess stderr 要約の全経路に通す。
- コピー先は `NINFS_WORKSPACE` (必須の絶対パス、無ければ作成) 配下のみ。形式拒否と正規化後の包含確認の二段構え。
- 依存バージョンは `pyproject.toml` に pin し、CLI 引数と出力名は Task 1 で照合する。
- ファイル内容は MCP 応答に含めない。`extract_code` はメタデータのみ返す。
- 各実装コミット後に `security-audit` を `quick` で実行し、`confirmed` を解消、`needs_validation` を確認する。完了後に独立 Review を受ける。

固定シグネチャ (全タスク共通、変更禁止):

```python
# policy.py
def resolve_dest(workspace: Path, dest_rel: str) -> Path: ...
def sanitize(text: str, secrets: Iterable[str] = ()) -> str: ...
def reject_write_args(extra: Mapping[str, Any]) -> None: ...

# runner.py
@dataclass
class InternalMount:
    kind: str          # "sd" | "sdtitle" | "ncch" | "exefs"
    mount_point: Path
    proc: Any          # Popen (mock可)
    handle_id: str | None  # このmountを確保した title_handle。sd は None

@dataclass
class MountSession:
    mount_id: str
    children: list[InternalMount]  # 確保順。解除は逆順
    title_handles: dict[str, TitleHandle]

@dataclass
class TitleHandle:
    handle_id: str
    mount_id: str
    requested_title_id: str
    resolved_title_id: str
    kind: str  # "base" | "update"

def detect_sd(sd_root_override: str | None = None) -> dict: ...
def mount_sd() -> MountSession: ...
def find_title(session: MountSession, title_id: str) -> TitleHandle: ...
def extract_code(handle: TitleHandle, dest_rel: str) -> dict: ...
def unmount(mount_id: str) -> dict: ...
```

公開応答の完全形 (Task 4 がキー集合まで試験する):

- `detect_sd` → `{"sd_root","has_n3ds_dir","has_boot9","has_movable"}` または `{"error":"ambiguous","candidates":[...]}`。
- `mount_sd` → `{"mount_id","mount_point"}` (内部の proc 等は含めない)。
- `find_title` → `{"requested_title_id","resolved_title_id","kind","tmd_found","title_handle"}`。
- `extract_code` → `{"dest_path","size","sha256","code_entry"}`。
- `unmount` → `{"ok","incomplete","errors_sanitized"}`。

`MountSession` レジストリ (`_SESSIONS: dict[mount_id, MountSession]`) とは別に、解除失敗残存を保持する `_RESIDUALS: list[InternalMount]` を持つ。公開IDの無効化と残存リソースの保持は分離する。`unmount`・再解除 (`retry_residuals`)・プロセス終了時 (`atexit`) は `_RESIDUALS` も対象とする。

環境変数: `NINFS_BOOT9_PATH`, `NINFS_MOVABLE_PATH`, `NINFS_SD_ROOT` (任意), `NINFS_WORKSPACE` (必須の絶対パス。Task 4 の起動時に検証・作成)。

## Review Focus

specが黙っているが利用者が当然期待する振る舞い。各行のテストは所有タスクに組み込み済み。

1. 常駐 mount 中も後続ツールが応答する → `mount_sd` はプロセス生存のまま返る (Task 2)。
2. `dest_rel` の `..` 成分・ドライブ・UNC は、内側に収まる場合も形式で拒否される → 拒否される (Task 1)。
3. ninfs の stderr に秘密フルパスや `Key: <hex>` が含まれても MCP 応答に出ない → マスクされる (Task 2)。
4. 圧縮 `.code` の ExeFS では展開済みが選ばれ、展開失敗は成功扱いされない → エラーになる (Task 3)。
5. 子mountの解除に失敗しても公開IDは無効化され、残存は再解除できる → `incomplete: true` + 再解除で回収 (Task 2)。

- [ ] **Step 3: Implement runner基盤**

`spawn_mount(argv)`: `Popen(argv, stdout=DEVNULL, stderr=PIPE, stdin=DEVNULL)`。`reject_write_args` 相当の検証は定数構築時に済ませ、起動時は read-only 定数が含まれていることを assert する。

`stop_proc(proc)`: `terminate()` → `wait(timeout=5)` → 残存なら `kill()` → `wait()`。
`detect_sd`: WinFsp 前提確認 (ninfs `_common` の FUSE import 可否。不可なら `RuntimeError("WinFsp/FUSE unavailable")`) → `NINFS_SD_ROOT` 指定時は単独検証 → 未指定時は `A:`〜`Z:` 列挙で `Nintendo 3DS` 保持者を収集 → 0件エラー / 1件採用 (4キー応答) / 複数 `ambiguous`。

`cleanup_core(mounts)`: 逆順に `stop_proc` し、失敗は収集して継続。戻り値は sanitizer 済み失敗文の list。
`unmount(mount_id)`: レジストリから即削除 (公開ID無効化) → `cleanup_core(session.children)` → 失敗残存は `_RESIDUALS` へ移動 → `{"ok","incomplete","errors_sanitized"}`。
`retry_residuals()`: `_RESIDUALS` を再解除し、回収数を返す。

解決順序 (仕様 §4 に一致。SD mount 上で選択してから子mountを起動する):

1. `session` の `sd` mount_point 配下でベース/更新ディレクトリ有無と TMD 一覧を読み取る。
2. 更新 (`0004000E...`) 存在なら更新優先。TMD複数時は更新 > バージョン最大 > 先頭。バージョンは TMD ファイル名/ヘッダの readable 値で比較し、同順位は辞書順先頭。
3. 解決後に `sdtitle → ncch → exefs` の順で `spawn_mount` (exefs には `--decompress-code`)。CXI 選択はタイトル内で最大サイズの `.cxi`、NCCH/ExeFS 入力はその CXI 由来のものとする。
4. 途中失敗は確保済みを `cleanup_core` で逆順破棄し、`TitleHandle` を発行しない。
